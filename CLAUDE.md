# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`issue-tracker` — a single-user desktop issue tracker built with [GPUI](https://github.com/zed-industries/zed) (Zed's UI framework) and the [gpui-component](https://github.com/longbridge/gpui-component) widget library. It owns its data in a local SQLite database; it is not a client for GitHub or GitLab.

Read `CONTEXT.md` for the domain vocabulary and `docs/adr/` for the decisions that shaped the architecture.

The project is GPL-3.0-only (`COPYING`), with one exception: `.agents/skills/` is vendored from `mattpocock/skills` and stays MIT under its own `LICENSE` and `NOTICE.md`. `.claude/skills/` symlinks into it rather than copying, so there is one set of files to keep that true of.

## Commands

- Build: `cargo build`
- Run: `cargo run`
- Check (fast type-check without codegen): `cargo check`
- Test: `cargo test`, single test with `cargo test <test_name>`
- Format: `cargo fmt`
- Lint: `cargo clippy`
- CI (`.github/workflows/ci.yml`) runs `fmt --check`, `clippy -D warnings` and `test --workspace` on macOS. It is the same three commands as above, so a green local run means a green CI run. A cold runner spends about six minutes building `gpui` from git; the cache makes the rest cheap.
- Install everything locally: `./scripts/install.sh`. Two `cargo install`s, because `issue-mcp` is a workspace member and `--path .` does not reach it — installing the app and then wondering why an agent cannot see the tracker is the failure it exists to prevent. `--locked`, so a fresh resolve cannot swap the `gpui` commit the tests passed against.
- Run the CLI: `cargo run --bin issue -- list` (or `./target/debug/issue` after a build). `cargo install --path .` puts both `Issues` and `issue` on the PATH. The CLI needs the app running and honours `ISSUE_TRACKER_DB`, since that is how it finds `api.json`.
- Run the MCP server: `cargo run -p issue-mcp`. It speaks JSON-RPC on stdin/stdout, so running it in a terminal looks like a hang — that is it waiting for a client. `cargo install --path crates/issue-mcp` puts it on the PATH; it is a *separate* install from `cargo install --path .`, because it is a workspace member.

Set `ISSUE_TRACKER_DB` to point at a scratch database when developing, so experiments never touch real issues:

```
ISSUE_TRACKER_DB=/tmp/it-scratch.db cargo run
```

Without it, the database lives in the platform data directory (`~/Library/Application Support/issue-tracker/issues.db` on macOS).

## Architecture

- **Module seam**: `domain` holds pure types and must not depend on `gpui` or `rusqlite`. `store` may depend on `domain`. `projection` and `api` may depend on both but **not** on `gpui` — that is what makes routing, auth and every mutation testable without a window or a socket. Only `ui` may reach for `gpui`. Don't erode this: `Entity<T>` needs `T: 'static`, not a `T` that knows about GPUI, so shared state can stay gpui-free and still be observable.
- **In-memory projection**: `Projection` (`src/projection.rs`) owns the `Store` and every Issue in a `Vec<Issue>`. `render()` reads only from it and never performs I/O. Mutations write through to SQLite *first*, then update the Vec — updating only one of the two is the characteristic bug here, and it shows up as a change that vanishes on restart. An existing Issue changes only through `Projection::commit`, which builds the next version as a clone and swaps it in once the write has succeeded; a new one is filed by `Store::insert` whole, row and Tags in one transaction, so a failed create leaves nothing behind. See `docs/adr/0002`.
- **One scan, not one per row**: an Issue does not know its own parts, so `Projection::sub_issues` scans the corpus — right for one Issue, quadratic for a list of them. Anything asking the same question of *every* Issue takes `Projection::sub_issue_index()` instead and reads `of_issue`/`settled_progress` off it: the issue list needs both a progress fraction and a `SizeRollup` per row, which was two full scans per row painted. Measured at 2,000 Issues in release, that render went from 4.6ms to 87µs. The index borrows the corpus and is built per render, never stored — a stored one is a second copy of what the Issues already say. `settled_progress` is a free function over `&[&Issue]` so the index and the scan cannot give different answers.
- **The projection is app-level, not window-level** (`docs/adr/0005`): it lives in a GPUI global (`src/app_state.rs`) so it outlives the window and the HTTP API can reach it. `IssueTracker` borrows it, renders from it, and `observe_in`s it. Reads therefore take `&App` — that is why `projection`, `selected_issue` and `count_for*` all carry a `cx`, and why `issue_list` collects owned `Row` values before building elements: the borrow must end before the element tree needs `cx` mutably. A path that reads the corpus *and* takes `&mut self` — every working-state change — goes through `IssueTracker::settling`, which clones the `Entity` **handle** so the borrow is of `cx` alone. Do not clone the Issues to escape that borrow: this is what `projection_issues` used to do, copying every title and body on every keystroke, every `j`/`k`, and every API write.
- **One settle path**: every mutation ends in `cx.notify()` on the Projection, which runs `IssueTracker::on_projection_changed` — prune the Tag filter, re-settle the selection, refresh the inputs. There is deliberately no separate branch for API-initiated changes. If you add a mutation, route it through `Projection` and let the observer do the rest rather than re-settling by hand.
- **Field-level patches**: `IssuePatch` names only the fields it changes, so two writers touching different fields can't clobber each other. A patch that changes nothing writes nothing, so `updated_at` doesn't move for a no-op.
- **Auto-save**: editing is debounced by storing the spawned `Task<()>` on the view and replacing it on each `InputEvent::Change`; dropping the old task cancels it. `InputState::set_value` deliberately suppresses change events, so loading an Issue into the inputs does not trigger a save.
- **Theme**: `gpui_component::init` pins the theme to Light unconditionally, so `src/ui/theme.rs` re-syncs it to the OS appearance — once inside the `open_window` closure before the first paint, then continuously via `observe_window_appearance`. Never hardcode a colour; every colour must come from `cx.theme()` or it won't follow the system into dark mode.
- **Named themes**: 21 theme files are vendored into `assets/themes/` and embedded with `rust-embed`; `src/ui/theme_catalogue.rs` parses them into per-mode lists. Light and dark are chosen *independently* because over half the upstream families ship only one mode — see `assets/themes/README.md`. Choices persist in the `setting` table (`docs/adr/0003`) via `Preferences`, and are applied at startup in `IssueTracker::new`. `Preferences` holds theme *names*, never resolved configs — what themes exist is the catalogue's subject, what was chosen is its own. Selecting a theme never changes *when* dark applies; that still follows the OS.
- **Sub-issues** (`docs/adr/0007`): a nullable `parent_id` column with `ON DELETE SET NULL`, so deleting a parent orphans its children without any code remembering to. Exactly one level deep, enforced from both ends in `Projection` — a cross-row condition no schema constraint can express, same situation as case-insensitive Tag identity. The completion rule is a real invariant, refused in *both* directions (a parent cannot go Done above outstanding work; a sub-issue cannot be reopened under a Done parent), where Done and Cancelled both count as settled. Attaching an Issue that already has a parent *moves* it — there is no separate operation — which is why pickers annotate candidates with the parent they'd be taken from. `Projection::may_attach` is the single statement of those rules: `set_parent` enforces it, and `eligible_sub_issues`/`eligible_parents` are defined as the Issues for which it returns `Ok`, so what a picker offers cannot drift from what the writer accepts. Its parent half is split out as `may_hold`, which is everything answerable *before the child exists* — that is what lets `Projection::create` take a parent and file the Issue under it in one write, so `POST /issues` with a `parent_id` refuses before anything exists instead of answering 404 to a caller it had just handed an Issue. Only **Done** constrains a parent; a Cancelled one takes work like any other Issue. Eligibility is deliberately *not* on the wire (`docs/adr/0010`) — every other surface learns the rule from the 409, which says it in prose.
- **Size** (`docs/adr/0011`): `Option<u8>` on an Issue, the only scalar that is not an ordinal enum — because a Parent's **Total size** adds its parts' Sizes to its own, and ordinals do not add. `u8` is the rule in the signature: work that will not fit in 255 is a tree of Issues, not a big Issue. A total is `u32` and `SizeRollup` is derived on every read, never stored, like the settled count. A Parent's own Size is *the work its parts do not cover*, which is the only reading under which adding is correct. Zero is a real Size and absent is not, so clearing needs a third state: `IssuePatch::size` is `Option<Option<Size>>`, `wire::PatchIssue` tells an absent key from an explicit `null` via `present_but_maybe_null`, and the CLI spells it `--size none`. `gpui::Size` is a width-and-height and collides under `use gpui::*` — qualify `issue_tracker::domain::Size` in `src/ui/`.
- **`WriteError`**: mutations distinguish `NotFound` (404), `Refused` (409) and `Store` (500). If you add a rule, return a `Refused` variant rather than an `anyhow` error, or the API will report a database failure for a request that was merely not allowed.
- **Pickers follow the selection**: `refresh_inputs` re-points the tag and relationship Comboboxes as well as the text inputs. It is the single place that answers "what does the selected Issue look like" — calling it from one path and the syncs from another is how those boxes came to show the *previously* selected Issue's answers.
- **Local HTTP API** (`src/api/`, `src/ui/api_server.rs`, `docs/adr/0006`): domain operations only — no view state. Hosted on a blocking `TcpListener` thread, one thread per connection, marshalled onto the main thread; there is no tokio runtime in this process and GPUI's executor has no I/O reactor, so don't reach for axum. `src/api/` is gpui-free and holds all the decisions; `api_server.rs` only moves bytes. A Tag name is the whole path remainder (`/issues/3/tags/ui/theme`), which is why routing is hand-written. Port and token are published to `api.json` beside the database, `0600`, token regenerated every launch — clients must read the file, not hardcode it. The endpoint surface is specified in `docs/openapi.yaml` (OpenAPI 3.1), written by hand and generated from nothing — a route, status or field added to `routes.rs` or `wire.rs` has to be added there too, or the spec quietly becomes fiction. Paths and methods are checked — `the_openapi_spec_describes_exactly_the_routes_there_are` fails on drift in either direction, and a new `Route` variant will not compile until `routes::template` names it — but statuses and fields are still on you. Bodies are framed by `Content-Length` only; `Transfer-Encoding` is refused with a 400 that says so, because reading a chunked body as an empty one tells the caller their `title` was missing.
- **Running the app while testing**: kill old instances first (`pkill -f "target/debug/Issues"` — keep it path-qualified, since bare `Issues` matches far too much). A stale instance keeps its window on top and will silently be the thing you screenshot, which looks exactly like a bug in the code you just changed. Also run `cargo build`, not just `cargo check`, before launching the binary.
- **Focus and keys**: navigation bindings (`j`/`k`/`c`/`e`/`x`/`/`, plus `t` tags, `s` sub-issues, `z` size) are scoped to the `IssueList` key context on a focusable list container, so typing into an input types text rather than navigating. The list is focused at startup; without that the bindings are dead until something is clicked. Two bindings on one key in one context is resolved silently in favour of one of them rather than reported, so check the list before adding one — `z` is Size because `s` was already taken. The size input is also not reachable by tabbing, since focus runs through the Status buttons first. `escape` and `cmd-b` are deliberately *unscoped* so they work while an input has focus.
- **macOS lifecycle**: the app follows macOS convention — closing the window does *not* quit (`QuitMode::Default` is `Explicit` on macOS). `main.rs` extracts `open_main_window` so `Application::on_reopen` can rebuild a window when the Dock icon is clicked. `cmd-q` flushes pending writes before quitting; so does `cx.on_release` when the window closes. Both matter because issue auto-save is debounced 400ms and would otherwise lose the last edit.
- **Menus** (`src/ui/menus.rs`): menu items dispatch actions, so anything in a menu needs a handler on `IssueTracker`. The View menu carries a checkmark on the active View, which means `menus::rebuild` must be called whenever the View changes — `set_menus` replaces the whole tree. The application menu's title comes from the **process name**, not from the first `Menu`'s name — which is why `Cargo.toml` declares `[[bin]] name = "Issues"`. Renaming that binary renames the menu.
- **Crate layout**: a workspace. `src/lib.rs` (`[lib] name = "issue_tracker"`) holds `domain`, `store`, `projection`, `api`, `operations`, `client` and `cli`; `ui` and `app_state` stay in the `Issues` binary. That is what makes the module seam structural — nothing in the library can name the view — so `src/ui/*.rs` imports from `issue_tracker::`, not `crate::`. Adding a `use gpui` anywhere under the lib re-erodes it.
- **The CLI** (`src/cli/`, `src/bin/issue.rs`, `docs/adr/0008`): a *client* of the HTTP API, never a second writer, so it fails with exit `3` when the app is not running rather than opening the database. Exit codes are load-bearing: `1` a refused or failed request, `2` a bad command line, `3` no API to talk to. The HTTP client is hand-rolled over `TcpStream` for the same reason the server is — loopback only, one request per connection, so end-of-stream delimits the body. Errors always go to stderr as prose, whatever `--json` says, so stdout is valid JSON or empty.
- **`pico-args` ignores what it was never asked for.** `src/cli/args.rs` ends every command with `rest()`, which calls `finish()` and rejects any leftover starting with `-`. Without it `issue set 7 --statuss Done` reports success and changes nothing. `issue --help` is likewise built from `Status::ALL`/`Priority::ALL` rather than written out, because a hardcoded list had already drifted from the domain once.
- **`operations` builds every request; `client` sends them.** `operations::list/get/create/update/delete/add_tag/…` are pure functions returning a `Call` — a method carrying its body, plus a path — and `Client::send` is the only way to perform one. They are separate modules because they are different subjects: `operations` knows the API's vocabulary and does no I/O, `client` knows sockets and timeouts and knows nothing about issues. Both the CLI and the MCP server go through it, which is what stops them drifting — the CLI had already stopped percent-encoding a Status where the MCP server encoded it. `list` takes a `domain::Narrowing` and the bodies are `api::wire::{NewIssue, PatchIssue}`, the server's own definitions, so a request's shape is stated once by the side that parses it. Those wire types need `skip_serializing_if` on every field, or a patch would send `"title": null` for something it never mentioned.
- **`operations::encode` is private, and the only encoder.** A slash survives in a path because a Tag name is the whole remainder there, and does not survive in a query value. There is no way to hand-build a path and get that wrong, because there is no way to hand-build a path.
- **The MCP server** (`crates/issue-mcp/`, `docs/adr/0009`): a *workspace member*, not a third `[[bin]]`, so `rmcp` and tokio are never compiled into the app — binaries in one package share one dependency table, and anything under `src/` would land in the library. It is a client of the HTTP API like the CLI, and shares `issue_tracker::operations` and `client` with it. Nine tools, one per domain operation; there is deliberately no `delete_issue`, because deleting erases a mistake and that judgement is the person's. Results are the API's JSON passed through untouched, except `list_issues`, which drops `body`.
- **Three things in `issue-mcp` that break silently.** The address file is read on *every* call, because the app regenerates its token each launch — cache it and the server works until you quit and reopen Issues, then fails looking like an auth bug. Nothing may write to **stdout**, ever: it is the JSON-RPC channel, and one stray `println!` from here or a dependency corrupts a message; `tracing` goes to stderr behind `RUST_LOG`. And every API call goes through `spawn_blocking`, because the client blocks for up to ten seconds and the app answers on the thread that paints the window.
- **Every entry point refuses fields it does not know.** The CLI calls `finish()`, the MCP server's arguments say `deny_unknown_fields`, and so does `api::wire::PatchIssue` — without it `PATCH {"statuss":"Done"}` answers `200 OK` and changes nothing, which is the one mistake a caller cannot see. `NewIssue` needs its own guard: `PatchIssue` arrives **flattened**, and a flattened struct never sees the keys it did not match, so `deny_unknown_fields` is silently inert there. It collects them into `unknown` instead and `create_issue` refuses a non-empty one. Adding a field to `PatchIssue` needs nothing; adding one to `NewIssue` must go *above* the flatten. `StatusArg`/`PriorityArg` build their JSON Schema `enum` from `Status::ALL`/`Priority::ALL`, so what an agent is offered cannot drift from what the tracker accepts.
- **`initialize` carries the domain's rules** as `instructions` — cancel versus delete, one level of sub-issues, the completion rule, case-folded Tags. It is glossary-derived prose: if `CONTEXT.md` changes, `INSTRUCTIONS` in `crates/issue-mcp/src/tools.rs` changes with it.
- **Sub-issue progress is on the wire**, as `settled_sub_issues` beside `sub_issue_ids` — the total is the list's length, so only the settled half is sent. It is the *whole* fraction regardless of the narrowing that produced the response, which is the point: `issue list --parent none` hides every child and still prints `[2/3]`. The CLI used to rebuild this client-side and issue a second `GET /issues` to repair it whenever a filter hid a parent's children. `IssueJson::new` takes the children themselves rather than ids and a count, so the two numbers cannot contradict each other.
- **`issue set` cannot change Tags, deliberately.** `PATCH {tags:[…]}` replaces the whole set, so changing one Tag through it is a read-modify-write; `PUT`/`DELETE /issues/{id}/tags/{name}` exists to avoid exactly that, and `issue tag add|rm` is the only route in. `issue new --tag` *is* fine — at creation there is nothing to clobber.
- **Tags**: derived, not records — a Tag exists exactly as long as some Issue carries it, so there is an `issue_tag` junction table and no `tag` table (`docs/adr/0004`). Two consequences bite. `Store::update` is transactional because the Issue row and its Tag rows must move together — the ADR-0002 half-written-change bug, with a second way to reach it. And case-insensitive identity (`Bug` *is* `bug`) cannot be a schema constraint, since a unique index on `issue_tag` is per-Issue; it lives in `domain::Tag`, whose `Eq`/`Ord`/`Hash` are hand-written over the folded key rather than derived. Route new names through `normalise_tags` or case variants will appear as separate sidebar rows.
- **Tag filter vs View**: a Tag filter is *not* a `View` variant. Views are the five predefined Status slices; a Tag filter is user-invented and narrows within whichever View is active. Because a derived Tag can vanish when its last Issue is retagged or deleted, `prune_tag_filter` runs on both paths — otherwise the list empties with the sidebar row you'd clear it from already gone.
- **Narrowing** (`domain::Narrowing`): the one rule for turning all the Issues into the ones asked for — a View, optionally within a Tag, a title match and a Parent filter. `WorkingState` holds one and the API builds one from its query string, so `?status=Doing&tag=ui` and clicking those two things in the window cannot diverge; they had already started to. It is a pure function over `&[Issue]`, tested in `domain`, and it preserves the order it was given, which is what makes "the first one" mean the same thing everywhere. Note `View::All` *is* "no status filter" — there is no `Option<Status>` anywhere. `count` exists beside `select` because a sidebar badge wants the number without materialising the rows.
- **Preferences** (`src/ui/preferences.rs`): the three keys that are *not* working state — `theme.light`, `theme.dark`, `sidebar.hidden`. Same shape as `WorkingState`: gpui-free, restored from a lookup, handed back as key/value pairs, with the writing left to the caller. `IssueTracker::persist` is the **only** place either of them is written, so "save a preference" has one shape and one failure policy: log and carry on. `choose_theme` used to return early on a write failure, which meant an unwritable settings table silently broke the theme picker; it now applies the theme first and remembers it best-effort. A theme never chosen is left absent rather than written as an empty string, so "never picked one" stays distinguishable from "picked one called nothing".
- **Working state** (`src/ui/working_state.rs`): a `Narrowing` plus the selection, with the rules that keep them consistent — settling a selection that fell out of view, pruning a Tag filter whose Tag has gone, and restoring all four from the `ui.*` keys (debounced ~400ms, since they change on every keypress). It is free of `gpui` and takes `&[Issue]`, so its tests build a `Vec` and need no window, store or database; `IssueTracker` supplies the corpus and does the GPUI half — `refresh_inputs`, the save, `cx.notify()`. It lives under `src/ui/` rather than in the library because working state is *per window* (`docs/adr/0005`) and no other surface has any: the API deliberately exposes no view state and the CLI has no selection to keep.
- **Sidebar toggle**: `cmd-b` or the `SidebarToggleButton` in the issue-list header drops the sidebar out of the element tree entirely (rendered as `Option`, not zero width), persisted as `sidebar.hidden`. The toggle button lives in the list header rather than the sidebar so it survives hiding. Because the sidebar owns both View navigation and the theme pickers, the header always shows the active View name — with the sidebar hidden it is the only thing naming it.
- GPUI apps are built from `Render`-implementing structs whose `render()` returns an element tree built with the `div()` builder API (flex-based layout, Tailwind-like modifiers such as `.size_full()`, `.flex_row()`, `.w(px(..))`).
- Returning elements from a helper that takes `&mut Context<Self>` usually needs `-> impl IntoElement + use<>` under Rust 2024, otherwise the return type captures the context lifetime and the borrow checker rejects the caller.
- `gpui_component::init(cx)` must be called once at startup before creating any windows — it registers the component library's global state/theme.
- The root view of a window must be wrapped in `gpui_component::Root::new(view, window, cx)`; `cx.open_window` takes a closure that constructs this root.
- `gpui-platform` (with the `font-kit` feature) provides the platform application entry point (`gpui_platform::application()`), separate from the core `gpui` crate.
- Both `gpui` and `gpui-component` are pulled directly from their git repos (not crates.io), so APIs may move; check the vendored source under `~/.cargo/git/checkouts/` (or run `cargo doc --open -p gpui -p gpui-component`) when an API isn't obvious from usage.
